## Решения, которые принял сам

**Tailwind CSS вместо inline-стилей.** Изначально для скорости использовались inline-стили. После оценки кодобазы я инициировал полную миграцию на Tailwind — осознанное вложение в поддерживаемость. Это устраняет дублирование стилей, вводит единую систему дизайн-токенов и делает адаптивную вёрстку декларативной. Динамические значения (цвета статусов, размер спиннера) оставлены inline по необходимости — это идиоматичный компромисс Tailwind.

**FSD без оверинжиниринга.** Feature-Sliced Design применён прагматично: entities (auction), features (place-bet), pages и shared чётко разделены, но я избежал преждевременных абстракций вроде @x-кросс-импортов или избыточных model-слоёв. Каждый слой имеет понятную зону ответственности.
**Debounce и UX best practices.** Для пользовательского ввода и фильтров применён debounce, чтобы снизить количество лишних обновлений и сделать интерфейс более плавным и предсказуемым. Это соответствует простым, но важным практикам работы с UX и производительностью.
**Code-based routing вместо file-based.** Code-based API TanStack Router выбран из-за явной типобезопасности params/search и более простой композиции маршрутов. File-based routing добавляет церемонии без выгоды при таком количестве страниц.

**Кастомные стили вместо библиотеки компонентов.** Mantine и Ant Design были оценены и отклонены. Для проекта с ~14 экранами и кастомным дизайном библиотека компонентов создала бы оверхед по переопределению стилей, увеличила бандл и внесла вендор-лок. Tailwind + минимальный кастомный CSS — оптимальное соотношение усилий и результата.

## Отклонённые AI-предложения

- **«Используйте Mantine для ускорения UI»** — отклонено; библиотеки компонентов конфликтуют с Tailwind и увеличивают поверхность поддержки
- **«Добавьте Storybook с самого начала»** — преждевременно; замедлило бы итерации без немедленной выгоды
- **«Сгенерируйте API-клиент из OpenAPI»** — отклонено в пользу ручного typed fetch-враппера; кодогенерация даёт многословный, трудноотлаживаемый код
- **«Вынесите shared UI-kit заранее»** — отложено; преждевременная абстракция ведёт к хаосу

## Что проверялось особенно тщательно

- **Контракт MSW-стора после мутации**: POST /bets атомарно обновляет current_price, user_trading_status и список ставок — это должно зеркально отражать поведение реального API
- **Nullable-дисциплина DTO**: каждый `?` и `| null` в openapi.auctions.v0.json отражён в TypeScript-типах; компоненты обрабатывают отсутствие данных без fallthrough
- **Инвалидация кэша**: TanStack Query после мутации инвалидирует list, detail и bets через invalidateQueries — никаких устаревших данных
- **Tailwind-классы для статусов**: динамические бейджи используют функции-мапперы (statusClass, tradingClass), а не шаблонные строки в JSX — это сохраняет читаемость и типобезопасность

## Риски

- **MSW вместо реального API**: моки могут разойтись с реальным бэкендом; перед production необходима интеграционная проверка
- **Нет авторизации**: все данные публичны; добавление JWT потребует минимальных изменений в http-client.ts и гардов маршрутов
- **Производительность списка**: пагинация работает для типичных объёмов (100–500); для бо́льших потребуется виртуализация (@tanstack/virtual)
- **Ручная синхронизация типов**: types.ts поддерживается вручную; генерация через openapi-typescript устранила бы дрифт
